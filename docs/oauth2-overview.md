# OAuth2 та OpenID Connect (OIDC)

---

## Що таке OAuth2?

**OAuth2** — це один із сучасних стандартів **авторизації**, який дозволяє одному застосунку (клієнту) отримати
**обмежений доступ** до ресурсів іншого застосунку або сервісу **від імені користувача**, **без передачі пароля**.

> Наприклад: ти заходиш на сайт і натискаєш «Увійти через Google»

### Які проблеми вирішує?

- Безпечна передача доступу без паролів
- Можливість делегувати доступ (наприклад, сервіс _A_ може отримати твої дані в сервісі _B_)
- Централізоване управління правами доступу

---

## Що таке OpenID Connect (OIDC) і до чого він тут?

**OIDC** — це **надбудова над OAuth2**, яка додає **автентифікацію**: дозволяє клієнту дізнатися, **хто саме** увійшов у
систему.

> Якщо OAuth2 — це «чи дозволити доступ до ресурсу»,  
> то OIDC — це «хто саме просить цей доступ».

🔹 Додає `id_token` — токен з інформацією про користувача (email, name, тощо)  
🔹 Працює через ті ж самі ендпоінти (`/authorize`, `/token`) що й OAuth2

---

## Основні компоненти системи

| Компонент                   | Опис                                       | Приклад                                            |
|-----------------------------|--------------------------------------------|----------------------------------------------------|
| **Resource Owner**          | Користувач, що володіє ресурсами           | Користувач e-commerce сайту                        |
| **Client**                  | Застосунок, що хоче отримати доступ        | Веб-сайт або мобільна апка або якийсь інший сервіс |
| **Resource Server**         | API, що перевіряє токени та надає ресурси  | API: `order-service`, `product-service`            |
| **Authorization Server**    | Видає токени                               | Keycloak, Auth0, Google                            |
| **Identity Provider (IdP)** | Сторона, яка підтверджує особу користувача | Keycloak, Google, Microsoft                        |

> У нашому випадку **Keycloak — це і Authorization Server, і IdP**  
> А наш **Spring Boot додаток - це Resource Server**

Крім Keycloak існує ще багато рішень, наприклад Auth0. Keycloak був вибраний бо його доволі легко запустити "з коробки"
і це можна перевикористати в інших проектах (скопіювати відповідний сервіс з [compose.yaml](../compose.yaml) та
імпортотувати конфіг [owu-ecommerce-realm.json](../misc/keycloak/owu-ecommerce-realm.json))

## Як відбувається інтеграція з іншими сервісами, де є облікові акаунти?

Інтеграція з Google, Facebook, Microsoft тощо **відбувається через IdP**.  
Keycloak, наприклад, може бути налаштований як посередник:

1. Користувач хоче увійти
2. Keycloak перенаправляє на Google
3. Google автентифікує користувача
4. Keycloak отримує результат, створює свою сесію, видає токен

Це називається **федерація** — коли IdP делегує аутентифікацію іншому IdP.

## Що таке Realm?

У контексті **Keycloak** (та інших IdP), **Realm** — це **ізольований простір автентифікації та авторизації**, який:

- Має власних користувачів
- Має своїх клієнтів (додатки)
- Має окремі налаштування політик безпеки, ролей, груп, протоколів

> Ти можеш уявити realm як окрему «організацію» або «тенанта».

---

### Для чого це потрібно?

- **Мультиорганізаційність**: наприклад, для SaaS-платформи, де кожен клієнт (компанія) має свій обліковий простір
- **Розділення середовищ**: напр., `dev`, `staging`, `prod` можуть мати окремі реалми
- **Ізоляція даних та налаштувань**: жоден користувач з іншого реалму не має доступу до поточного

---

### Приклад:

У Keycloak:

- Маємо `realm = owu-ecommerce`
- У цьому реалмі:
    - Користувачі: менеджери, постачальники, покупці
    - Клієнти: SPA (web-client)
    - Ролі: `SHOP_MANAGER`, `SUPPLY_MANAGER`, `USER`
    - Мапінг до Google як зовнішнього IdP (треба налаштувати)

Коли запит іде до:

```
https://localhost:8080/realms/owu-ecommerce/.well-known/openid-configuration
```

— це означає, що ми працюємо в межах **реалму `owu-ecommerce`**, а не глобальної конфігурації сервера.

---

## Що таке `.well-known/openid-configuration`

Це URL, що вказує на OpenID конфігурацію сервера (впринципі є стандартом, тому
в [application.yaml](../src/main/resources/application.yaml) достатньо вказати
`http://localhost:9090/realms/owu-ecommerce` для `issuer-uri`):

```
http://localhost:9090/realms/owu-ecommerce/.well-known/openid-configuration
```

Він повертає JSON з:

- `authorization_endpoint`
- `token_endpoint`
- `userinfo_endpoint`
- `jwks_uri` — URL відкритого ключа для перевірки токенів
- `scopes_supported`, `grant_types_supported`, тощо

## Grant Types

**Grant Type** — це спосіб, яким клієнт отримує токен. Різні сценарії = різні типи.

### 1. Authorization Code + PKCE

**Найбезпечніший та найрекомендованіший для клієнтів із UI.**  
Особливо актуальний для SPA (Single Page Applications) та мобільних апок.

**Переваги:**

- Високий рівень безпеки (PKCE захищає від перехоплення authorization code)
- Працює з браузером
- Можна використовувати без `client_secret`

**Як працює:**

1. Клієнт генерує `code_verifier` і `code_challenge`
2. Перенаправляє користувача на сторінку логіну (`/authorize`)
3. Користувач логіниться, дає згоду → отримає `authorization_code`
4. Клієнт надсилає `code_verifier` + `authorization_code` до `/token`
5. Отримує `access_token` (+ `id_token` якщо OpenID)

[Детально про це можна прочитати тут, бо це той спосіб який показано на відео і яким скоріше за все будеш користуватися](oauth2-auth-code-flow.md)

---

### 2. Client Credentials

**Підходить для server-to-server взаємодії.**  
Коли немає користувача — тільки система.

**Переваги:**

- Проста реалізація
- Безпечно передавати `client_secret` в бекенді

**Як працює:**

1. Сервіс (client) надсилає `client_id` + `client_secret` на `/token`
2. Отримує `access_token`
3. Застосовує токен для запиту до іншого API (resource server)

**Приклад:**

- Мікросервіс `order-service` надсилає запит до `product-service`

---

### 3. Refresh Token

**Дозволяє отримати новий `access_token` без повторного логіну.**

**Переваги:**

- Покращує UX (користувач не мусить логінитися заново кожні декілька годин)
- Підтримує довготривалі сесії

**Як працює:**

1. Після логіну, клієнт отримує також `refresh_token`
2. Коли `access_token` закінчився, клієнт надсилає `refresh_token` на `/token`
3. Отримує новий `access_token`

---

### 4. Device Code Flow

**Рішення для пристроїв без клавіатури або браузера (наприклад, Smart TV, IoT).**

**Як працює:**

1. Пристрій запитує код авторизації (`device_code`) у `/device_authorization`
2. Виводить код на екран + інструкцію (введіть код на іншому пристрої)
3. Користувач на іншому пристрої вводить код → логіниться
4. Пристрій отримує токен

**Приклад:**

- YouTube на телевізорі показує: “перейдіть на youtube.com/activate і введіть код”

---

### 5. ⚠️ Resource Owner Password Credentials (ROPC)

**Передбачає, що користувач вводить логін і пароль прямо в застосунок.**  
**Небезпечний, не рекомендований до використання.**

**Як працює:**

1. Клієнт надсилає `username` і `password` прямо на `/token`
2. Сервер видає `access_token`

**Ризики:**

- Клієнт має доступ до пароля користувача
- Не можна відокремити автентифікацію від авторизації
- Суперечить принципу довіри
